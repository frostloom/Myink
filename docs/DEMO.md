# 项目演示与验证说明

## 项目定位

面向连续创作的工作台，重点是状态管理、可审计的一致性检查，以及失败后恢复。当前是已部署的小范围邀请试用 MVP，上线证据见 REMAINING-WORK；不将测试替身表现或历史 smoke 等同于当前版本真实质量。

- [离线历史执行案例](interview/agent-execution.html)：直接在浏览器打开，筛选审核/路由/人工修订/落库，展开已留存 detail，无需登录或模型密钥。
- [Archify 流转图](diagrams/README.md)：当前已提交代码的流程，附源证据与验证回执。
- [本轮验收](evaluations/interview-p0-verification.md)：本轮实际检查，不能以历史全量结果替代。

重建离线案例：根目录运行 `python scripts/render-interview-demo.py`。默认读取 `docs/evaluations/workflow-recovery.json`，不连数据库、不调用模型；输出含源 SHA-256。该历史真实模型记录使用纯合成现实题材：先生成检修故事，再人为植入超能力，拒绝后进入修订、重新抽取、校验、审核、落库。它不是原始全量轨迹：没有完整正文、prompt、耗时/价格和准确模型版本，因此不能伪造逐字 diff 或计算质量改善幅度。

五分钟讲解：一分钟说明问题与流程图；两分钟浏览正常节点与工具/审核证据；一分钟浏览人工拒绝后的 revise 和 persist 失效统计；一分钟解释可靠性、评测边界及下一步对照实验。现场实时生成使用另一个测试作品，不修改演示证据，涉及模型费用时预先确定范围。

## 推荐演示顺序（约 10 分钟）

1. **建书与约束**：展示已有作品的世界观、大纲、人物卡片，说明哪些设定由作者确认。
2. **生成编排**：预先准备一次批次任务，展示规划、写作、抽取、校验、审核、落库的节点记录，以及耗时和模型 usage。不要现场依赖外部模型一定及时响应。
3. **人工确认和续跑**：展示等待审核任务与候选池，解释 checkpoint 如何保留进度。实际演示前用自己的测试作品走通一次。
4. **编辑可靠性**：改正文后切章再切回，展示草稿恢复；打开同一章的两个标签页，先在 A 保存，再在 B 保存，展示 409 冲突以及服务器正文对比。
5. **记忆与校验**：展示事实、人物状态、关系图与伏笔；说明低风险候选自动处理，高风险候选需要人工确认。
6. **验证证据**：运行前端测试或展示本次回归记录，打开并发保存和上下文预算测试，解释它们防止的具体故障。

## 不能混用的指标

40 条冲突样例中的 21/26 检出、0/14 误报是机制测试基线。LLM 判定和 embedding 使用替身，且部分阴性测试没有对应检测机制。它不支持“真实小说矛盾检出率 80.8%”或“误报为零”的结论。

模型调用 usage/耗时是真实接入后的运行记录；单元测试中的 token 数与耗时可能是固定的替身数据。展示时要标明来源。未做压力测试前，不宣称具体 QPS、并发用户数或高可用水平。

## 下一阶段：真实模型效果评测

以下是尚未执行的验证方案，不是已有结果：

- 固定模型版本、提示词版本、采样参数与题材；每个条件重复多次，记录失败与人工介入。
- 先用短篇小样本校准标注标准，再在不同题材连续生成 30–50 章；保存初稿与人工修改稿。
- 对照条件至少包含完整系统、关闭混合召回、关闭复盘；每次只改变一个模块。
- 指标包括每万字矛盾数、桥段重复、伏笔兑现、人工修改量、每章成本、耗时及失败率。
- 由人工盲评标注证据，模型评审只作辅助；报告样本量、模型配置、平均值和波动。
- 原始稿件、标注、配置、运行记录一并保存，形成可重现报告。

## 后续优先级

1. 真实模型与长篇数据上的效果评测，先证明核心模块带来的改善。
2. 修复已知漏检：经历矛盾、物品状态、伏笔兑现、能力前置规则、势力归属。
3. 作者效率：选段改写、差异预览、正文与记忆同步状态、已有稿件导入。
4. 计划公网试用时，再做正式账户、迁移、备份恢复和运维监控。
