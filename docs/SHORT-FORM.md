# 短篇形态：整篇一次成稿

2026-09-21。为 Myink 增加短篇形态的决策记录。参照实现是 [Narcooo/inkos](https://github.com/Narcooo/inkos) 的短篇管道（`packages/core/src/pipeline/short-fiction-runner.ts`、`agents/short-fiction.ts`、`prompts/short-fiction.ts`）。

本文是**决策文档**：设计逻辑与分界不随代码演进失效；行号只作检索锚点。

## 结论

1. **短篇不是「放宽阈值的长篇」，是一条平行的管道。** 参照实现就是这么做：它的短篇三个文件不复用长篇任何 agent（长篇有 architect / chapter-analyzer / continuity / detector / settler / state-validator / consolidator / chapter-review-cycle 等一整套机器，短篇零复用）。
2. **根因是「短篇没有跨章」。** 原有一致性机器（台账、伏笔池、事件表、L1/L2、audit、全局审计）存在的理由全是「跨章要保持一致」。短篇整篇在一次调用里同时产生，一致性由注意力保证，不需要外部台账——所以**整个一致性审核层可以不存在**，而不是「需要调参让它别误报」。
3. **审核降到一次，且是编辑视角。** 可机检的跨章矛盾不存在了，剩下的只有「好不好看」。
4. **参数**：1–10 章，全书总量 ≤ 2 万字，每章 1000–8000 字；**章数少则每章长**（见 §5）。
5. 新增一个形态字段记录「这本书走哪条管道」——这次理由比「放宽阈值」硬：两条管道的差异是结构性的，不是参数性的。

## 一、设计逻辑：一条逻辑推出全部选择

长篇的每一台机器都服务于同一个前提：**第 8 章不能和第 1 章矛盾，而模型写第 8 章时看不见第 1 章**。台账、伏笔池、事件表、连续性校验、状态校验，都是在补这个信息缺口。

短篇消掉了这个前提：**整篇在一次调用里同时产生**，模型写第 8 章时第 1 章的文本还在它自己的上下文里。

参照片的五个设计选择都是这一条推出来的：

| 选择 | 推出它的理由 |
|---|---|
| 整篇一次写 | 一次写完，一致性是免费的；拆章写才需要台账 |
| 每章短（900–1200 字） | 整篇要塞进一次输出。章短是**果**，不是因 |
| 审稿只一次、编辑视角 | 无跨章矛盾可机检，只剩「好不好看」 |
| 确定性检查只剩字数 | 长度可确定，好看不可以 |
| 改稿是整篇重写而非打补丁 | 改一章会波及别章的呼应铺垫；整篇重写才不留缝 |

改稿那条的原文写得很直白：「不要只列修改建议，不要只改几章片段，输出完整正文」。

## 二、参照片的五步

1. **方案（大纲）** —— 验收标准不是「结构完整」，是**信息密度够不够写手一次成稿**。原文：「章节方案必须足够密，写手拿到后能直接一次写完」。逐章写清：标题方向、关键场面、角色动作、压力升级或回报、章尾继续读的理由。另有硬要求「故事要完整，不是长篇前 5 章启动包」——短篇最典型的失败就是写成长篇第一卷。
2. **审纲** —— 独立角色，只判一件事：能不能支撑一次写完整篇。**改一次**；失败则保留 v001，并落一份 warning 说明「系统没有用残缺输出覆盖它」。
3. **成稿** —— 一次调用 + 宽容解析器。解析器每章四级回退（tagged block → markdown 标题 → … → 合成标题），内容全失败留空字符串。**格式坏 → 内容为空 → 补写**，不抛异常。补写把已写正文与缺失章号一起回喂，有次数上限。
4. **审稿** —— 整篇一次，编辑视角。检查项：标题、章节标题、开篇、人物动机、时间线、人物关系、证据/权限、压力递进、反派反扑、**后半段是否泄气**、结尾回报是否落地。prompt 明写「不要把审稿变成确定性打分」。没有伏笔回收、没有台账比对——因为没有台账。
5. **改稿** —— 整篇重写，一次；失败保留首稿。

另外两个值得照搬的机制：

- **六个阶段各自独立配模型**（方案 / 审纲 / 写手 / 审稿 / 改稿 / 打包），另有兜底模型。
- **运行快照与断点续跑**：已存在定稿大纲就直接从成稿阶段接。

### 解析取向与 Myink 现行做法相反，这是有意的

Myink 现在走**严格契约**（Pydantic + `_parse_json` 挡坏数据、坏数据拒绝但不崩）。短篇整篇一次输出，格式漂移概率远高于按章输出，用同一套严格契约只会在长输出上频繁失败。参照片的做法是**从宽解析 + 事后再修**：解析失败降级成「该章内容为空」，再用 `findEmptyShortFictionChapters` 这个可确定的状态触发补写。短篇沿用后者。

## 三、与长篇的分界

```
长篇：write → extract → 台账 → 下一章 recall → validate(L1/L2) → audit → route
短篇：方案 → 成稿 → 审稿 → 改稿 → 落库        （中间没有任何持久化状态）
```

这句对比是整份方案的价值所在。Myink 侧要**显式不跑**：`extract`（不抽事件 / 伏笔 / 关系 / 人物状态）、`recall`（无台账可召回）、`L1` / `L2` / 单章 `audit` / 全局审计、待确认池（短篇的产物是成稿，不是候选记忆）。

这条要写死在代码路径里，不能靠「没有数据所以不触发」——否则以后有人加了数据流，短篇会静默地开始跑一套为长篇设计的检查。

## 四、Myink 侧的落地

**新建**

- `workflow/short_runner.py`：五步，整篇粒度。**不走 `chapter_graph`**——短篇没有「章」这个调度单位。
- `prompts.py` 增 `SYSTEM_SHORT_PLAN` / `PLAN_REVIEW` / `WRITER` / `DRAFT_REVIEW` / `REVISER`。
- 分块解析器：`=== CHAPTER N CONTENT ===` 抽块 + 多级回退 + 空章补写。
- `validation/short.py`：只做每章字数的双区间 observation。

**复用**

- 题材包（`genre_catalog`）、`ProjectSettings`、建书草稿流程。
- 章表 + 章节版本表：成稿后按块拆章落库，前端展示与导出照常可用。**短篇的「版本」语义是整篇版本**（v001 / v002），对齐参照片的 `drafts/v001.md`、`drafts/v002.md`。
- LLM 调用层与 `record_run` 成本记录。角色集需扩（方案 / 审纲 / 写手 / 审稿 / 改稿 / 打包）；想先省事可收成三个（planner / writer / reviewer）。

**形态字段**

`Project` 加一列记录管道归属（默认长篇，存量书零影响）。仓库已有幂等补列范式，见 [db.py:201](src/myink/db.py#L201) 的 `users.tier`。

## 五、参数

### 联合约束（本次定下的规则）

用户给「章数」和「每章字数」，系统按一条规则校验：

```
章数 × 每章字数 ≤ 20000        # 总量上限，一次输出的硬约束
每章字数 ∈ [1000, 8000]        # 单章下限保证写得出完整场面；上限再长就该拆章
```

超限时按比例压每章字数并告知，而不是拒绝。这条规则自然给出「章数少则每章长」：

| 章数 | 每章字数上限 | 全书总量 |
|---|---|---|
| 1 | 8000 | 0.8 万 |
| 2 | 8000 | 1.6 万 |
| 5 | 4000 | 2 万 |
| 10 | 2000 | 2 万 |

1 章时整篇即一章（8 千字），符合「只想写一章就写长一些」。

### 为什么总量卡在 2 万

参照片的 token 算式：

```
maxTokens = max(12288, ceil(章数 × 每章字数 × 2.2) + 4096)
```

12 章 × 1000 字 → 30,496 token。

Myink 侧这条路是通的：`MODEL_REGISTRY` 里 `deepseek-v4-flash` / `deepseek-v4-pro` 声明的输出上限是 384,000 token（[base.py:59-62](src/myink/providers/base.py#L59-L62)），而 `_bounded_generate` 只用 `request_token_budget=64000` 卡**输入**（[nodes.py:149-164](src/myink/workflow/nodes.py#L149-L164)），输出由 `max_tokens` 单独管。所以 2–3 万 token 的整篇输出没有制度性障碍。

但**不加总上限不行**：10 章 × 3000 字 = 3 万字 ≈ 4.3 万 token（Myink 的 1.43 系数）或 7 万（参照片保守的 2.2 系数），超出且后半段质量会塌。而超长单次输出最容易掉的正是审稿 prompt 专门盯的那个问题——**后半段泄气**。

### 字数观测区间

参照片是**两套机制**，别混为一谈：

- **输入夹取**：`boundedInteger` 把每章字数夹进 900–1200。
- **事后观测区间**：`scaleRangeDelta` 以 `REFERENCE_TARGET=2200` 为基准缩放，soft `±300`、hard `±600`。目标 1000 字时 soft 864–1136、hard 728–1272。

Myink 侧建议**复用现有的比值口径**（[service.py:24-25](src/myink/validation/service.py#L24-L25) 的 `_LEN_LOW_RATIO=0.8` / `_LEN_HIGH_RATIO=1.3`），不自造一套新系数；注意参照片的区间比这个更严。区间只记 observation，不阻塞——短篇没有 revise 循环去消化它。

## 六、落地顺序

1. 形态字段 + 参数校验（联合约束）
2. `short_runner` + 五个 prompt：打通 **方案 → 成稿 → 审稿 → 改稿** 最小闭环
3. 分块解析器 + 空章补写 + 字数 observation
4. 按块拆章落库（章表 + 整篇版本）
5. 前端：建书表单加短篇分支；进度页对齐现有批次页
6. 端到端：一篇 5 章 × 2000 字

## 七、验证

- **第一道门禁**：先用一篇 2 万字的稿子实测单次输出不被截断。注册表声明 384k，但真实上限取决于所配端点。这一关不过，整套「整篇一次成稿」不成立，不必往下走。
- 喂一个**被截断的输出**，应得到「部分章为空 → 触发补写」，而不是崩、也不是静默落库半成品。
- 断言短篇路径下 `agent_runs` 中**没有** extract / audit 记录——证明记忆层真的没跑。
- 长篇回归全绿：`EMBED_ENABLED=0 python -m pytest tests/ -q`。

## 八、风险

- **单次输出上限未实测**（见验证第一条）。
- **没有 recall 意味着 runner 自己管上下文**：方案 + 已写正文一起进 prompt，写第二版时输入近乎翻倍，`request_token_budget=64000` 的输入闸门要盯着。
- **后半段质量**是整篇一次成稿的固有弱项，参照片靠审稿 + 改稿两步兜，这两步不能省。
- **静默退化**：短篇下没有全局审计也没有一致性检查，界面上若不给任何提示，用户会以为「审过了没问题」。审稿结果是唯一出口，必须显示出来。

## 九、待定

1. 角色集先收成三个（planner / writer / reviewer）还是直接上六个（对齐参照片的独立模型配置）。
2. 每章 8000 字的上限是否合适——1 章 8 千字、2 章各 8 千字，是否该改成「章数 ≤ 2 时才放开上限」。
3. 短篇是否需要导出为单文件（`full.md` + `short-story.json`，对齐参照片的产物形状）。
