# 自动团队开发流程

## 用户如何使用

在 Myink 主会话中发送：

> 按团队流程执行：实现【具体需求】。请自动完成调研、方案、开发、独立测试和缺陷修复，最后交付结果。

用户无需手动复制各阶段产物。主代理保持当前任务的上下文，安排交接并汇总结果。这是代理执行约定，不是后台常驻服务；会话停止或工具不可用时不会自动在后台继续运行。

## 主代理的执行规则

1. 检查当前工作目录、Git 分支、HEAD 和已有改动，界定用户需求。列出简短阶段计划。
2. 为当前需求选用唯一的任务标识，在 `docs/work-items/<任务标识>/` 保存交接记录。复用同一任务的记录，避免覆盖其他任务。
3. 按下列角色逐阶段调度。调用子代理时必须写明任务目标、工作目录、允许修改范围、输入文档、预期交付物和禁止递归派生团队的要求。
4. 调研期间，主代理独立检查环境、现有验证入口和受影响组件。开发期间，主代理检查验收覆盖、准备测试环境或检查集成约束；测试期间，主代理审查差异及交付记录。只在存在可独立并行的有用工作时派出子代理，不为形式上的分角色空转。
5. 阶段依赖串行执行。等待并读取前一角色结果后，才启动依赖其交付物的下一角色；主代理必须把结果显式写入后续派发消息，不能假设不同子代理自动共享聊天记录。
6. 普通技术取舍由主代理决定并记录；仅在重大需求歧义、必要授权或凭证缺失、确实无法解决的外部依赖阻塞时联系用户。能够继续的独立工作继续完成。

## 调研角色

输入：用户需求、当前代码、现有说明与测试。

职责：调查现状，明确目标、非目标、约束及可验证的验收标准。必要时比较架构方案，给出推荐方案、受影响组件和执行任务清单。只修改当前任务的方案文档，不修改产品代码。

交付：`brief.md`，包含需求、架构方案、假设、验收标准及任务清单。主代理检查是否足以执行，普通方案直接进入开发。

如果当前环境确实提供 Spec Kit，读取其适用说明后使用，记录并引用它实际生成的文档，不重复维护两套需求。不可用时直接编写上述文档，不因缺少 skill 阻塞流程，也不编造命令。

## 开发角色

输入：`brief.md` 或其引用的 Spec Kit 文档、主代理确定的方案、允许修改范围。

职责：完成实现和必要的针对性测试，保持最小改动。发现需求冲突时回报主代理；不得静默修改验收标准以适应实现。

交付：代码修改和 `implementation.md`，列出修改文件、实现与验收项的对应关系、实际执行的命令和结果、已知限制，以及工作目录、分支和 HEAD。未提交成果需明确标为未提交，附本轮文件范围及差异说明，不能把 HEAD 当成全部修改的版本标识。

交付后暂停修改产品代码，等待测试结果。默认交付工作区差异，不自行创建提交。

## 测试角色

输入：原始需求和验收标准、开发交付说明、对应代码目录及版本状态。

职责：独立检查验收项，运行实际测试并检查异常路径和回归风险。可在分配范围内补充必要测试，但不修改产品实现。先确认测试对象与开发交付一致，测试过程中不得有其他代理修改被测产品代码。

交付：`verification.md`，记录每项验收的通过、失败、未验证或环境阻塞状态，测试命令、退出结果、跳过情况和被测版本状态。缺陷应给出复现步骤、预期与实际行为、严重程度及相关位置。

只读检查或测试替身不能冒充未执行的集成测试。验证入口见根目录 `AGENTS.md`；不在开发或生产数据上运行会清理数据的测试。

## 修复与交付

- 测试失败：主代理将缺陷交回开发角色；开发修复并更新交付记录；测试角色复验受影响验收项与必要回归。
- 不以固定轮数或已有部分通过作为完成依据。重复失败时调查根因并调整方案；只有需要用户提供信息或外部条件改变时才报告阻塞。
- 主代理最终检查改动范围、验收覆盖和实际测试证据，报告已完成内容、验证结果与剩余限制；未满足验收不得宣称完成。
- 最终交付不默认包含提交、推送、合并和发布，除非用户已授权。

## 工作目录与分支

- 单一需求默认顺序共享当前工作目录，同一时间只有开发角色修改产品代码。子代理并不天然拥有独立 worktree。
- 多个开发方向并行时使用独立 worktree，各自命名分支默认以 `codex/` 开头；不要让多个代理在同一目录切换分支。
- 新 worktree 通常只包含所选提交中的文件。若当前有未提交修改，先确定这些修改是否属于新任务基线；不得擅自丢弃、批量提交或假定它们已被复制。
- 并行架构方案使用相同的需求基线和验收标准。测试绑定具体成果版本，不对仍在变化的目录做最终验收。
- 没有隔离数据库、端口与队列时串行运行集成测试；不同目录不代表服务资源已经隔离。
