# 服务器上用 Pi 做 Myink 的对照迭代

> **状态：草案，未做。** 每日「先对照、再改一个点、第二天看有没有变好」这条循环已经对齐。时间、权限、脚本边界、先看哪些数、质量评测怎么接，都还没拍板，下文用 **待定** 标出。

日期：2026-10-10

这份文档记录想在腾讯云那台一直开着的机器上，用 Pi 照看 Myink。Pi 是终端里的编程代理外壳，自己不做推理；模型以后再选。选它是因为外壳小、循环能改、命令在本机执行，笔记本合上也不影响定时任务。不在这里比较费用。

## 一、已经对齐的循环

一天一轮，一次只改一个点。同时改两处时，第二天分不清是谁起的作用。

1. **前一天，服务和数据库还开着。** Pi 读取当时正在跑的版本和一份数据快照，对照上一份快照，从数据里找出一个值得改的点。
2. **写下决定。** 决定里要有：当前版本、拿来比的上一份快照、哪个指标变了、预期它往哪边动、准备改哪一个模块。没有这份决定，不进入升级。
3. **夜里升级。** 只实施决定里的那一个改动。白天站点对外开着；夜里停掉对外服务，把内存让给构建，做完再把站点拉起来。
4. **第二天，用新数据复核。** 新快照只回答一件事：昨天改的那个指标有没有按预期动。没有动，就停在这一轮，不接着改别的。有动，才从当天的数据里再选下一个点。

「真正的开发」指的就是这一圈，不是每天换一次镜像。

## 二、现场事实

下面是 2026-10-10 看到的情况，用来约束方案，不是要写死的配置。

| 事实 | 当时的情况 |
| --- | --- |
| 机器 | 腾讯云 `62.234.106.6`，4 核，内存约 3.6GB；服务开着时已用约 1.2GB，可用约 2.4GB，另有约 1.9GB 交换空间 |
| 磁盘 | 系统盘 40GB，当时剩余约 26GB |
| 对外站点 | `https://62.234.106.6`，Caddy 提供 HTTPS。`/readyz` 检查 Redis、数据库、worker |

| 镜像 | `myink-api:local` 给 api 和两个 worker 共用，Dockerfile 里是 `pip install`。`myink-caddy:local` 单独构建，里面包含 `npm ci` 和前端构建 |
| 数据库备份 | crontab：每天 03:17 跑 `/home/ubuntu/myink/backup.sh`，产物在 `/home/ubuntu/myink/backups/`，约 3MB 的 `myink-*.sql.gz`。当天已有 10 月 10 日那份 |

停掉 api、worker、Caddy、Redis、RabbitMQ 之后，多出来的主要不是一大块空闲内存，而是构建若把内存顶满，没有线上进程会被杀掉。Postgres 在纯构建镜像时用不到。数据在卷里。

## 三、一轮里面发生什么

时间点和由谁触发都 **待定**。顺序先按这个来想，避免「库已经停了才开始找数据」。

### 3.1 快照（数据库还开着）

Pi 把「此刻正在跑的版本」和一组数字写成一份快照，和上一份放在一起。版本用容器上的 `org.opencontainers.image.revision`，不要用仓库里还没部署的提交冒充线上版本。

快照放哪、留多少份、文件格式，**待定**。需要能按日期找回，也不能跟数据库备份混在一个目录里互相覆盖。

### 3.2 对照

对照只比较相邻两份快照，以及这份决定里点名的那一个改动。Pi 要写出：

- 线上版本，和上一份快照的版本
- 哪个指标变了，变了多少
- 这个变化够不够作为「值得改」的理由
- 若值得改：只改哪一个模块，预期哪个指标往哪边动
- 若不值得改：今天不升级，理由是什么

「变化够不够大」的门槛 **待定**。没有门槛之前，决定可以先由人看报告后再说升不升。要不要每天都允许 Pi 自己进入升级，**待定**。

### 3.3 升级

只有 3.2 的决定写明了「升」以及改哪一处，才进入第四节的夜间步骤。决定为「不升」时，机器保持白天的运行方式，Pi 只留下报告。

第二天的快照用来核对预期。对不上就停止继续改，先解释为什么对不上。解释本身要不要再改代码，**待定**，默认是先停。

## 四、现在能对照的数，和还不能下的结论

### 4.1 库里已经有的运行记录

管理观测已落在数据库里，见 [ADMIN.md](../ADMIN.md)。这些可以做相邻两天的对照，但含义不要说满：

| 记录 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| `cost_est` | 已记下的费用估算有没有上升或下降 | 不是供应商账单。缺价格的历史记录不能补成真实花费 |
| `duration_ms` | 已测量的节点耗时 | 零值可能是没测到。任务从创建到最后更新的跨度含排队、暂停和人工等待 |
| token、缓存命中 | 调用规模和缓存是否命中 | 不能单独当成文笔变好 |
| 降级、重试、失败、预算暂停 | 运行是否更不稳，或预算是否经常打断 | 不能换成「矛盾变少了」 |
| `/readyz`、磁盘、容器是否在跑 | 站点当时是否健康 | 不代表生成质量 |

快照里具体收哪几列、按章还是按天聚合、要不要分用户，**待定**。读取用只读查询。账号环境、模型密钥、密码不进快照。

### 4.2 写作质量

[DEMO.md](../DEMO.md) 里写过、但还没做成每晚自动实验的对照是：每万字矛盾数、桥段重复、伏笔兑现、人工修改量、每章成本、耗时、失败率。条件是固定模型版本和提示词，一次只关或只改一个模块，原始稿和配置留下来。

这些数不能从 4.1 推出来。费用下降不能写成「文写好了」。历史评测归档也不能当成今天的基线，见 [评测资料入口](../evaluations/README.md)。

质量对照做不做、用现有 `scripts/evaluate.py` 还是另起一份小样本、谁来做人工复核，**待定**。在这件事情定下来之前，Pi 的「有没有提升」只覆盖 4.1 里事先点名的运行指标。

## 五、夜里把站点让出来

白天对外服务。夜里停服务，是为了让构建有一块不会误伤线上进程的时间，也接受这段时间打不开网站。停多久、从几点到几点，**待定**。只有一个硬约束：不要卡在 03:17 前后，那时备份脚本要连着 Postgres。

建议的机械顺序如下。其中「谁来执行、是一条脚本还是 Pi 逐步下命令」**待定**。不管怎么执行，失败后都要在早上之前用停机前的镜像把站点拉起来。

1. 确认当天的对照决定是「升」，并且只含一个改动。
2. 停入口之前，先看有没有正在写的章节任务。是等它结束，还是允许中断，**待定**。
3. 记下 api、worker、Caddy 当前镜像标识，作为回滚目标。
4. 停应用容器。构建期间若也不需要数据库，再停 Postgres。用 `docker compose stop`。不要 `down -v`，不要删卷。`caddy-data`（证书）和 `backups/` 不动。
5. 分两次构建，不要两个镜像一起建。先建 Python 镜像（api 与两个 worker 共用这一份），再单独建 Caddy 镜像（前端构建在这一步，内存最高）。Node 堆要不要设上限，上限多少，**待定**。设上限的意图是：构建失败可以重来，不要让系统先杀掉别的进程。
6. 按依赖启动：Postgres，Redis，RabbitMQ，然后 api 与 worker，最后 Caddy。worker 要不要一个一个换，**待定**；共用同一个镜像，所以不必构建三次。
7. 看 `/readyz`，并核对新容器的 revision 是不是这次决定里的版本。
8. 任一步失败：用第 3 步记下的镜像把原来的服务拉起来，并在报告里写明停在哪一步。不要空着等到白天。

构建缓存和旧镜像会占磁盘。清到什么程度、保留最近几个可回滚镜像，**待定**。

GitHub 上已有的 CI 还要不要作为「允许构建之前」的门，**待定**。服务器上这份构建是为了在这台机器里完成替换，不代替那条契约检查。

## 六、Pi 上准备什么

先不装权限插件、沙箱包、日程包。`pi-routines` 一类要会话一直开着才到点；`pi-sandbox` 一类会停下来等人点允许。这和「跑完就退出」不一致。以后若要加一道权限闸，再单独立项。

最小内核只有读文件、改文件、写文件、执行命令。要补的是规矩和材料，不是另一套常驻服务。

| 准备 | 作用 | 状态 |
| --- | --- | --- |
| 服务器上的一份 git 工作区 | 现在没有检出，Pi 看不到要构建的代码 | 要有。克隆位置、用哪条分支、谁有推送权限，**待定** |
| 一份启动就读到的项目说明 | 写明本机边界：不删卷、不动备份和证书、没有对照决定不升级、一次只改一处 | 形式 **待定**（`AGENTS.md` 或其他 Pi 能在启动时读到的说明） |
| 快照与对照的说明 | 告诉 Pi 去读哪些数、快照长什么样、决定要包含哪几项 | 做成按需加载的技能或一段固定提示，**待定** |
| 夜间替换步骤 | 把第五节的顺序固定下来，避免每晚重新发明 Docker 命令 | 独立脚本，或写在技能里由 Pi 逐步执行，**待定** |
| 系统定时任务 | 调用 `pi -p`，结束就退出。24 小时开着的是服务器，不是 Pi 进程 | 几点跑、一天跑几次，**待定**。必须避开 03:17 的备份 |

模型供应商、是否固定某一个模型、会话要不要跨天保留，**待定**。跨天对照靠的是快照文件，不靠 Pi 记得昨晚的对话。

## 七、还没拍板的问题

实现前需要单独决定的，集中在这里。上面各节里的 **待定** 是同一批事情，不另起一套。

1. 每天自动升级，还是 Pi 只出报告、人点头之后才停服务？
2. 运行指标先看哪几列？写作质量评测什么时候接、谁复核？
3. 变化到多大才算「值得改」？第二天怎样算「有提升」？
4. 夜间窗口的起止时间，以及正在写的章节是等待还是中断？
5. 工作区放哪、Pi 用哪个系统用户、Docker 权限给到整份套接字还是只给一条替换命令？
6. 替换步骤做成脚本，还是允许 Pi 在说明约束下自己执行？
7. 构建前要不要先过 GitHub CI？Node 构建的内存上限设多少？旧镜像留几份？
8. 快照放哪、留多久？本机那份过期的备份副本要不要重新拉齐（这是备份的事，不是 Pi 的循环）？

## 八、不在这份草案里做的事

- 不把 Pi、OpenClaw、Rakazo 或 Grok Bot 装到正在对外服务的机器上。这份文档只记录打算。
- 不把 Grok Bot 或别的云端电脑当成这条循环的执行者。命令要在这台服务器上发生。
- 不在未做对照的夜里换镜像。
- 不把 `cost_est` 或耗时写成写作质量结论。
