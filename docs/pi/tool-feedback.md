# 固定检查失败反馈

Pi 通过受控 `run_check` 检查当前候选代码。检查没有通过时，工具回执仍为 `blocked`；其中 `evidence.check_feedback` 可提供下一步修复所需的诊断。失败反馈不能批准候选或发布。

目前适配的是捕获数据的固定检查及其完整基线/候选配对。反馈包含检查、候选、计划和版本的精确身份，四项指标的通过/失败数量，以及固定失败类别。它不包含案例正文、预期答案、私有路径、原始输出或任意错误信息。

| 字段 | 用途 |
| --- | --- |
| `metrics.trace_fidelity` | 实际 JSON 编码字节预算内，是否保留应当完整留存的文本 |
| `metrics.redaction` | 凭据脱敏检查结果 |
| `metrics.encoded_caps` | 编码大小及预留空间检查结果 |
| `metrics.input_immutability` | 捕获过程是否保持业务输入不变 |
| `remediation_codes` | 固定类别，例如 `byte_fidelity`、`credential_leak`、`truncation_flag` |
| `paired_objective_passed` | 失败反馈恒为 false，不是验收凭证 |

每项指标为 `{pass:数量, fail:数量}`。Pi 应根据失败类别分析源码，取得最新文件/候选哈希后修改并重新检查。工具执行中的候选变化、身份不符、不完整配对、未验证执行、未知类别或超大报告会拒绝诊断投影；此时应排查执行问题，不能把空反馈理解为测试成功。停止的会话不直接重放，继续执行需要新的宿主授权和运行身份。

维护入口是 `ops/pi/tools.py` 的 `_failed_check_feedback`，测试入口是 `ops/pi/tests/test_check_feedback.py`。扩展其他固定检查时，需增加明确的宿主报告契约与对应反例；不要直接转发原始日志或接受模型提交的检查结果。最终验收仍由 `verify_stopped_phase` 核对最后一次补丁之后、精确当前候选的真实成功检查。

本轮离线针对性回归覆盖104项，包含反馈持久化/幂等重放、恶意或畸形字段、泄露防护、大小限制、检查过程中版本变化，以及失败反馈无法通过最终验收。用历史真实022报告验证了格式兼容；这不等于新一轮真实 Pi 已通过，也不表示整体项目或上线验收完成。

开发完成顺序统一为：最后一次成功 `apply_patch` → 当前候选的成功 `unit run_check` → `candidate_status({})`。最终状态必须绑定相同候选 ID、base、generation、哈希，并包含该成功检查回执。再次修改会使两者失效；缺失、过期或先于最终检查的状态不能完成开发。宿主停止后认证整个会话及工具账本，不代替 Pi 补调工具。
