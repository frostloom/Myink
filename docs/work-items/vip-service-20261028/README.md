## 已实现

- 管理员账号详情可手动开通、取消 VIP，不含支付、到期或自动续费。
- 模型最低会员等级 `normal` / `vip`；旧模型默认为所有会员可用。
- 普通默认模型沿用 `model_routes`，VIP 覆盖使用 `vip_model_routes`。
- 模型目录、用户设置保存、操作就绪检查、最终 provider 解析均校验服务器当前会员等级。
- 管理员模型分配页可调 VIP 与普通用户的调度权重，各 1–10，默认 3:1。
- 独立 `FairScheduler` 已测试：两队列忙时按权重取消息；空队列让出容量。比例代表每个 worker 的调度机会，不代表执行耗时或全局完成时间。
- VIP FIFO 队列和独立延迟回投队列；普通队列保留原 RabbitMQ 参数，无须删除已有队列或数据卷。
- 批次在 `bridge` 持久化已完成章节进度后重新排队；确认续跑消息成功后才 ACK 原消息。续跑不增加 retry_count，不重复扣配额、不释放并发占位。
- 手动续跑、预算扩容和计划确认使用当前会员等级选择队列；暂停/取消与章节让出竞争时保留用户操作。
- 删除 VIP 默认模型会清除对应 VIP 路由；停用在用模型、把普通默认模型直接改为 VIP 专用有明确提示。

## 消费循环验收

用户批准后已接入双队列拉取，补齐真实 RabbitMQ + Redis + Worker 进程验证：单 Worker 3:1 调度、双 Worker 在 100 条 VIP 积压时处理普通任务、2 秒协商心跳下阻塞 5 秒仍可确认、SIGTERM 只完成当前任务、进程被杀后的 VIP 消息重投、发布确认丢失时续跑不丢失。
真实章节流程也已验证 VIP 与普通两类任务都完成正文生成，且每个任务只执行一次 persist。
额外先复现再修复两项边界：AMQP 事件泵断连不能进入任务错误 ACK 分支；事件泵收到 SIGTERM 后不能再拉取下一条消息。
最终全量回归与第二轮独立审查结果见 progress.md。
第二轮审查还发现手工恢复后的自动 `batch_resume` 可能越过后来的暂停；已通过失败回归复现并修复，所有 paused 任务都等待显式恢复。

## 将来部署注意

远程部署与合并需另行授权。本轮未提交、未推送、未合并；本机部署已获用户明确授权并完成。
完成后升级须协调 API 与全部 worker，避免新 API 投 VIP 队列而旧 worker 无法消费；新 worker 继续读取旧普通队列以排空遗留消息。
若回滚旧版本，须先处理新 VIP/延迟队列中的积压；不能直接删除消息或 RabbitMQ 数据卷。
模型等级与会员等级互相独立：开通 VIP 不会自动把一个模型标成 VIP 专用，管理员需在模型编辑中指定。
未配置某 VIP 环节时沿用该环节的普通分配；普通环节缺省时沿用普通写作模型。
本期不增加新的供应商故障回退链，现有重试保留；所有实际选用模型仍必须通过会员等级检查。
